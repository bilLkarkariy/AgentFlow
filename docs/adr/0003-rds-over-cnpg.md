# 0003 — RDS on AWS, CloudNativePG on kind; Redis and RabbitMQ always in-cluster

## Status

Accepted, 2026-09-06.

## Context

AgentFlow needs PostgreSQL (workflow definitions, run state, migrations), Redis
(BullMQ queues and the Socket.IO adapter) and RabbitMQ (the `agentflow.flow-run`
work queue between api and worker).

Two environments with opposite properties:

- **kind**, on a laptop, free, no cloud account required. Anything that needs
  AWS is unusable here.
- **EKS**, on **spot** nodes that can be reclaimed with two minutes' notice
  ([ADR 0002](0002-eks-spot-graviton-public-no-nat.md)), destroyed after every
  demo.

The question is not "operator or managed service" in the abstract. It is: what
happens to each of these three when a node disappears mid-demo?

## Decision

| Component | local (kind) | aws (EKS) |
|---|---|---|
| PostgreSQL | **CloudNativePG** `Cluster agentflow-db`, 1 instance, 2 GiB | **RDS** `db.t4g.micro`, pg16, 20 GiB gp3, single AZ, `rds.force_ssl=1` |
| Redis | StatefulSet, `redis:7-alpine`, 1 GiB PVC | same, `gp3` |
| RabbitMQ | StatefulSet, 3.13 with the prometheus plugin, 2 GiB PVC | same, `gp3` |

The switch is one value: `postgresql.cnpg.enabled: false` in
`deploy/envs/aws/infra.yaml`. Everything else about the application is identical,
because the application only ever sees an environment variable:

- local: Secret `agentflow-db-app`, key `uri` (generated by CloudNativePG)
- aws: Secret `agentflow-db`, key `POSTGRES_URL` (projected by External Secrets
  from Secrets Manager)

with `POSTGRES_SSL=false` locally and `true` on AWS, because RDS is configured to
reject non-TLS connections.

None of these three pods gets an Istio sidecar
(`sidecar.istio.io/inject: "false"`): they speak raw TCP, the mesh brings them
no routing and no useful telemetry, and a sidecar would only add a slower start
and a second thing to debug when the database will not come up.

## Consequences

**Positive**

- The database — the only thing here whose loss is not recoverable by
  rescheduling — is not on a spot node.
- RDS costs 0.022 USD/h and removes storage, backups, failover, minor version
  upgrades and TLS termination from the demo's surface area entirely.
- CloudNativePG still gets demonstrated, every day, on the local cluster: an
  operator, a `Cluster` CR, generated credentials, `-rw`/`-ro`/`-r` services,
  and WAL archiving to S3 if it is switched on. It is a talking point *and* a
  running thing, not a slide.
- `rds.force_ssl=1` forced the `POSTGRES_SSL` environment variable to exist,
  which is the kind of thing that is much cheaper to discover in a demo than in
  a migration.
- Redis and RabbitMQ stay in-cluster in both environments, so the GitOps tree,
  the NetworkPolicies and the dashboards are identical.

**Negative**

- **Two Postgres code paths.** The local one is an operator with generated
  credentials; the AWS one is a Terraform resource with a password in Secrets
  Manager. Two ways for the same thing to break, and the AWS one is only
  exercised when someone spends money.
- RDS lives in the ephemeral stack, so **the data does not survive
  `make aws-down`**. That is correct for a demo and would be catastrophic
  anywhere else; `deletion_protection = false` and `skip_final_snapshot = true`
  say so explicitly.
- Redis and RabbitMQ are **single pods with a PVC**. No replication, no quorum
  queues, no Redis Sentinel. A spot reclamation of their node loses in-flight
  queue state and, with the Socket.IO adapter, live run updates.
- `backup_retention_period = 1` on RDS is the minimum that keeps automated
  backups on at all. It is not a recovery strategy.

## Alternatives considered

**CloudNativePG on EKS too** — appealing for symmetry, and CNPG is genuinely
good: it does failover, PITR and backups to S3 properly. Rejected because it
would put the only stateful thing in the system on interruptible capacity. CNPG
would handle a node loss correctly *with three instances across three AZs*,
which is exactly the topology this demo does not have. Running it with one
instance on one spot node would be a worse story than RDS, not a better one.

**Aurora Serverless v2** — scales to a low ACU floor and would be elegant, but
the floor is still ~0.06 USD/h *per ACU-hour* with a 0.5 ACU minimum, roughly
double `db.t4g.micro`, and it adds a cluster/instance layer for no demo value.

**ElastiCache and Amazon MQ** — the managed equivalents of the other two.
Rejected on cost (ElastiCache `cache.t4g.micro` is ~0.016 USD/h, Amazon MQ far
more) and because the demo genuinely benefits from having stateful workloads
*inside* the cluster: they are what the NetworkPolicies, the PVCs, the
StorageClass choice and the "why no sidecar here" conversation are about.

**RDS locally via a tunnel** — would make one code path, at the cost of
requiring an AWS account to run the local demo. That breaks the "free, on a
laptop, offline" property, which is the whole reason the local cluster exists.

**SQLite** — the api already supports it for unit tests. Not a candidate for
anything with a migration story.

## In production I would

**PostgreSQL** — RDS Multi-AZ, or Aurora PostgreSQL once read scaling matters.
`deletion_protection = true`, `backup_retention_period` 14-35 days,
point-in-time recovery, `final_snapshot_identifier`, cross-region automated
backup replication, and a **restore rehearsal in CI**: a scheduled job that
restores the latest snapshot into a scratch instance and runs a query. A backup
nobody restores is a hope.

Credentials via **IAM database authentication** rather than a stored password,
and separate roles for the migration Job and the application, so a runtime
compromise cannot alter the schema.

**Redis** — ElastiCache with a replica and automatic failover, or Valkey. Move
the Socket.IO adapter onto it so the api can actually run more than one replica,
which is currently the reason `replicaCount: 1` is honest rather than lazy.

**RabbitMQ** — a proper cluster: the RabbitMQ Cluster Operator, three nodes,
**quorum queues**, a dead-letter policy, and `PodDisruptionBudget`s. Or Amazon
MQ if nobody on the team wants to own it.

**Everywhere** — encrypted with customer-managed KMS keys, expand/contract
migrations only (so an application rollback never needs a schema rollback), and
a written RPO/RTO that someone has agreed to.
